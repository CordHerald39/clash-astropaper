电脑端 Clash Verge Rev 的仓库里，正式 Release、历史上的 Alpha，以及 AutoBuild 会同时出现。很多人把“构建更新、标签更靠前、带预发布或滚动字样”理解成“官方更推荐”。官方对发行版的划分说明，预发布通道和正式推荐通道用途不同，不能互相替代。

## 官方如何划分发行通道

仓库 README 用表格回答“我应当怎样选择发行版”。Stable 是正式版，特征是高可靠性，适合日常使用，下载入口是 Release 页面。Alpha 被明确标为废弃，用途是测试发布流程。AutoBuild 是滚动更新版，适合测试反馈，并写明可能存在缺陷。

因此，“预发布”在这里至少覆盖两类：已经废弃的 Alpha，以及仍可用于测试的 AutoBuild。它们面向流程验证或缺陷反馈，不是面向稳定日常使用。Release 页上带完整版本号（资料中可见 v2.5.7、v2.5.6、v2.5.5）并给出分平台安装包的，才是正式通道产物。

同一份正式版说明里，Windows 还把安装包分成“正常版本(推荐)”和“内置 Webview2 版”。后者体积较大，仅在企业版系统或无法安装 Webview2 时使用。这是运行环境适配，不是“预发布更新所以更该装”，也不能用包体积或文件名里的 extra 字样去推断推荐等级。

## 判断该用哪一类的适用条件

按官方文字，判断依据是通道用途，而不是构建时间谁更新。

日常使用、要可靠性：走 Stable，到 Release 页下载对应系统的正式安装包。Windows 优先选标注为“正常版本(推荐)”的 64 位或 ARM64 包；只有企业版或装不了 Webview2 时才考虑内置 Webview2 包。macOS 按芯片选 aarch64 或 x64。Linux 按发行版选 deb 或 rpm，并按架构选 amd64、arm64 或 armv7。Debian 系用 apt 加本地路径安装，Redhat 系用 dnf 加本地路径安装，这些是正式页给出的包类型说明，不改变“正式推荐仍是 Stable”这一前提。

愿意承担缺陷、目的是测试反馈：才考虑 AutoBuild。官方已写明可能存在缺陷，因此它不等于推荐给所有人的最新版，也不等于把正式版尚未合并的修复提前交给日常环境。

看到 Alpha：按官方标注视为废弃通道，不要当成当前推荐安装源，也不要因为它仍能打开下载页就当成备用正式版。

另外，正式发布说明写明 Windows 不再支持 Win7。系统版本不满足时，改下预发布或滚动包不能当作兼容方案。架构也必须和本机一致：常用桌面是 64 位包，ARM64 被标为不常用，选错架构与选错通道是两类问题，应分开处理。

## 选错通道或安装失败时的下一步

若当前装的是 AutoBuild 或历史 Alpha，出现内核起不来、服务模式异常、TUN 不可用、系统代理状态读失败一类情况，下一步不是继续追更新的预构建，而是回到 Release 页，改用当时的正式版本号安装包。正式说明里对 Windows、macOS、Linux 分别列出了服务、TUN、权限、内核退出和日志相关的修复；这些条目是随正式标签发布的，不能默认某一份滚动构建已经包含全部条目。

若架构选错，按同一正式版本下的架构列表重下，而不是换到 AutoBuild 碰运气。若 Windows 上“正常版本”因缺少 Webview2 无法运行，再按官方限定条件改用内置 Webview2 包，而不是改用预发布。Linux 则核对 deb/rpm 与 CPU 架构是否匹配后再装。

安装说明和常见问题，官方指向文档站；判断“预发布是否等于正式推荐”这件事，仍以仓库 README 的发行版表格，以及 Release 页的“正常版本(推荐)”标注为准。先定通道，再定系统和架构，最后才选具体安装包。
