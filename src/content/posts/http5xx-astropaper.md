## 先放回 5xx 这一类，再谈三个码的层次

讨论 Clash 订阅更新里的 500、502 与 503，首先要承认它们同属 **服务器错误响应（500–599）**：请求已到达能说话的 HTTP 服务器，但没有按成功类（200–299）完成。它们不是客户端错误（400–499），也不是重定向（300–399）。MDN 还指出 500 是“泛化”的：服务器遇到不知如何处理的情况，并且找不到更合适的 5xx 才用 500。因此 500 与 502、503 并列时，500 往往表示“本跳已经出错，但没有更精确的码可报”，不能理解成比 502、503 更严重的同一个故障。

适用条件：日志或响应行里出现的是这三个标准码之一。若实际是 504（网关未能及时取得响应）、501（方法不被支持）或未列出的非标准码，不要并进这三层模型。订阅更新通常是 GET 一份资源；下面的层次划分针对“谁在这次 HTTP 交换里失败”，不涉及本地如何解析配置文本。

## 500、502、503 分别钉在哪一跳

500 Internal Server Error 钉在 **当前这台源站（或最后处理者）自身**。它表示该服务器遇到无法处理的状况，又给不出更贴切的 5xx。含义是：问题发生在生成最终应答的这一层内部，而不是“我作为网关，上游回了坏数据”，也不是“我暂时不想接请求”。对订阅更新而言，500 指向提供该 URI 的服务端处理失败， mand 不能从状态码反推出客户端构造了错误请求——那一类应出现 400–499。

502 Bad Gateway 钉在 **网关/反向代理这一跳与它的上游之间**。定义是：服务器作为网关去取处理请求所需的响应时，得到了无效响应。发 502 的这一跳当时在履行网关职责，并且已经从更后面拿到了“无效”的东西。它不证明网关进程完全死掉（死掉往往连 502 都回不出），而证明上游应答无法被当作合法响应使用。订阅链路里常见多层代理，502 说的是“下一跳回包无效”，不是本机 Clash 配置项写错。

503 Service Unavailable 钉在 **当前这台服务器的就绪状态**。服务器尚未准备好处理请求，常见原因是维护或过载。文档强调这应用于临时状况，并应在可能时用 `Retry-After` 给出预计恢复时间；同时还提醒注意缓存相关头，因为这类临时响应通常不应被缓存。503 与 500 的差别是：503 承认“现在不能处理”且偏向可恢复窗口；500 是内部已出错且没有更细码。503 与 502 的差别是：503 说的是本跳未就绪，502 说的是本跳已作为网关工作但上游无效。

## 怎样判断有没有分层分错，以及分错时下一步

判断依据：只看到 500 → 停在“当前处理者内部、无更精确 5xx”，不要自动翻译成网关。只看到 502 → 停在“网关拿到无效上游响应”，不要改成维护窗口。只看到 503 → 停在“本跳未就绪/过载/维护”，并检查 `Retry-After` 与是否被缓存。GET 若最终是 200，资源已获取并在消息体中传送，说明该次已离开这三层错误。

易混项要单独剔除：504 与 502 同属网关视角，但 504 是等不到，不是拿到无效包。429 是客户端在时间窗口内请求过多，属于 4xx。304 是缓存未修改，不是服务端故障。分层失败时，下一步是回到响应行核对数字本身，而不是按体感把三个码当成同义词。数字一变，层次就要重画，不能沿用上一轮的 503 维护结论去解释新的 502。
