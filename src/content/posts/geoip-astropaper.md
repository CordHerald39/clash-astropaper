`GEOIP` 在官方说明里只回答一件事：匹配 IP 所属国家代码。它不匹配注册主体，不匹配证书组织，也不匹配 Geosite 域名集合。把 IP 地理数据读成「网站所属公司」，是把三条完全不同的数据叠成了一条。遇到「公司在一地、地址在另一地」时，应按规则类型改问题，而不是要求国家代码去代表公司。

## GEOIP、GEOSITE 和 ASN 各自回答不同问题

`GEOSITE` 匹配 Geosite 内的域名，文档注明部分内容参考 v2fly/domain-list-community。它回答的是这个域名在不在某类域名列表里。列表可以按服务名组织，例如文档示例 `GEOSITE,youtube,PROXY`。这仍然不是公司工商信息，只是域名集合是否包含该名字。

`IP-ASN` 匹配 IP 所属 ASN，回答的是这个地址落在哪个自治系统。ASN 的运营者可以是运营商、云厂商或企业网络，和网站品牌没有一一对应关系。`IP-CIDR`、`IP-CIDR6`、`IP-SUFFIX` 只回答地址是否落在给定范围。`GEOIP` 只回答国家代码。适用条件应当分开写：要按域名服务集合分流，用 `GEOSITE` 或 `DOMAIN*`；要按地址段，用 CIDR 或 IP 后缀；要按自治系统，用 `IP-ASN`；要按 IP 的国家代码，才用 `GEOIP`。

文档里的域名示例包括 `google.com`、`baidu.com`、`ad.com` 等，它们出现在 `DOMAIN`、`DOMAIN-SUFFIX` 和逻辑规则中，匹配的是字符串形态的域名，不读取公司总部，也不读取 IP 地理。判断依据是：一条规则的类型字段已经规定了数据对象，不能用「这家网站是哪国公司」这类业务常识去改写类型含义。

## 域名走到 GEOIP 时，手里只剩某一个 IP

域名开始匹配关于目标 IP 的规则时，mihomo 触发 DNS 解析，用得到的目标 IP 检查是否匹配。因此 `GEOIP` 看到的是解析结果那个地址的国家代码。同一域名在不同解析路径上可以落到不同地址，国家代码随之变化。这和「网站所属公司」相对稳定的直觉不是同一件事。公司主体不会因为一次解析改注册地，但 `GEOIP` 会因为换了一个 IP 而换一个国家代码。

`no-resolve` 会跳过这次解析；若更早规则已经解析过，带 `no-resolve` 的目标 IP 规则仍可匹配。具体操作：当用某公司官网域名去做地区判断时，先确认匹配走到 `GEOIP` 时手里到底有没有 IP、是哪一次解析给出的 IP。没有 IP 就不会用国家代码；有 IP 则只对该 IP 的国家代码负责。附加参数 `src` 还会把对象改成来源 IP，那时国家代码描述的是客户端地址，与网站公司更无关系。

`SRC-GEOIP` 直接匹配来源 IP 所属国家代码。适用条件是识别访问者地址的地理分类，不是识别目标网站的公司国籍。把来源国家当成站点归属，属于对象选错。`SRC-IP-ASN` 同样只用来源地址的 ASN，不能用来证明目标站点由哪家公司运营。

## 阅读配置时如何避免把公司、域名和 IP 国家写混

规则从上到下匹配。若 `DOMAIN-SUFFIX,google.com,auto` 写在 `GEOIP` 之前，命中后根本不会用该域名去问 IP 国家代码，出站由域名规则决定。这并不能证明公司在某国或不在某国，只证明后缀先匹配。逻辑规则同样如此：`AND`、`OR`、`NOT` 组合的是规则类型和 payload，文档要求注意括号，组合结果仍不是公司实体。`SUB-RULE` 只决定是否进入子规则，也不提供所属公司字段。

失败时的下一步应当改问题，而不是改国家代码去贴近公司名。若目标是按服务域名拦截或放行，应使用 `DOMAIN*` 或 `GEOSITE`，并接受它不代表公司法人。若目标是按服务器地址所在国家，应使用 `GEOIP`，并接受它不代表运营公司注册地；同时核对 DNS 是否发生、`no-resolve` 是否让规则没见到 IP。若目标是按网络运营者，应使用 `IP-ASN`，不要把它读成国家或公司品牌。所有规则都不中则 `MATCH` 接手，它无需条件，更不包含公司信息。

进程名、路径、UID、入站类型等规则匹配的是本地发起者或入站通道，与网站所属公司无关。它们若排在 `GEOIP` 之前，地区数据不会被问到。文档还指出请求为 UDP 而节点没有 UDP 支持时会继续向下匹配，这时最终出站可能和任何「公司所在地」想象都无关。排查「为什么不像某公司所在地」时，把类型字段、匹配对象（域名、目标 IP 或来源 IP）、解析是否发生、优先级四项写下来，即可停止用公司总部去解释 IP 国家代码。
