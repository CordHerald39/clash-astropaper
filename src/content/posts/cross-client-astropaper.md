电脑端多个客户端常常都能读取 mihomo 风格的 YAML，这只说明内核输入语言相近，不说明图形界面、服务封装和覆写管道相同。不能因为共享内核语法，就把主题、TUN 开关、DNS 覆写、Merge 脚本或备份同步当成必然可迁移的同一功能。以下说明只依据 Clash Verge Rev 的产品定义和发布说明。

## 适用条件

当你因为「都是 Clash Meta / mihomo 内核」而准备复用界面能力、服务模式或覆写结果时，应把内核层和 GUI 层分开评估。仓库把项目定义为基于 Tauri 2 的 Clash Meta GUI，内核是内置的 Clash.Meta（mihomo），并可切换 Alpha 内核。YAML 进入内核前，还要经过该 GUI 的配置管理、系统代理守卫和服务进程模型。系统范围是 Windows（x64/x86）、Linux（x64/arm64）和 macOS 11+；Windows 安装包不再支持 Win7。这些约束属于应用分发，不是内核语法的一部分。

## 内核语法覆盖什么，界面另外做了什么

内核语法处理的是送给 mihomo 的配置文本。界面层在 Features 中单独列出：自定义主题颜色、代理组与托盘图标、CSS Injection、配置文件管理和增强（Merge 和 Script）、语法提示、系统代理和守卫、TUN、可视化节点和规则编辑、WebDav 配置备份和同步。WebDav 是客户端同步能力；Merge 与 Script 会在送入内核前改写配置；TUN 与系统代理守卫依赖操作系统权限和服务，不会因为某一行代理类型相同就自动具备。

发布说明里大量缺陷发生在 GUI 与服务层，而不是 YAML 字段本身。DNS 覆写开关按订阅独立记忆，自动关闭仅影响当前订阅；扩展覆写窗口需要提示作用范围、执行顺序和应用设置优先级；系统服务在升级后版本或协议不兼容时会提示重新安装；读屏把侧边栏导航播报为不可用控件；规则编辑会把首字母转成大写。这些行为在内核文本完全相同的情况下仍会出现。

服务模式与 Sidecar 是界面用来拉起内核的进程模型。开发说明写明开发通道会保留服务安装状态，未安装则走 Sidecar。发布说明中的普通权限无法启动内核、服务残留、重装后内核缺失、无法继续使用 Sidecar，都属于「谁来启动内核」。共享一份出站列表解决不了服务未装或权限被误判。Windows 还区分正常安装包与内置 Webview2 包，这决定界面能否运行，与规则写法无关。

## 判断一项能力属于内核还是界面

依据有三条。第一，该能力是否出现在 Features 里且带有 GUI 修饰，例如主题、托盘、可视化编辑、WebDav、Merge、Script、守卫。第二，故障是否按 Windows、macOS、Linux 分段，并提到服务、TUN、系统代理、Webview2 或安装包。第三，修复是否针对覆写记忆、编辑器、读屏、首页是否显示服务模式等界面状态。满足任一条，就不应因为内核相同而假定另一客户端可复现。Stable 与 AutoBuild 的可靠性声明也只约束该 GUI 的发布节奏，不能推导成内核语法契约。

## 失败时下一步

若迁移后配置能载入但功能找不到或行为不同，应停止在 YAML 里寻找对应键，改为对照 Features 逐项确认目标客户端是否声明了 Merge、Script、TUN、WebDav、DNS 覆写等封装，再用发布说明核对当前版本是否把相关封装当作已知缺陷。需要观察内核本身时，应在尽量关闭 GUI 覆写的前提下看内核能否启动，而不是把界面开关写进配置文件冒充内核字段。核对订阅时只保留已有链接中的 `token=示例` 片段，用于确认查询参数是否被客户端改写。
