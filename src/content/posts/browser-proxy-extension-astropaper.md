浏览器扩展一旦自行指定 http 或 socks 代理，该浏览器内的请求往往不再跟随操作系统代理，而是直接打向扩展里填写的地址和端口。Clash 内核在全局配置中提供的正是这类入站，并叠加上验证、运行模式和进程匹配。因此扩展配置会改变浏览器行为，不是因为手册记载了扩展产品，而是因为流量入口和进核后的匹配条件变了。适用条件是：电脑端内核已按全局配置监听代理端口，同时浏览器启用了指向这些端口或指向其他地址的扩展。

## 入口从系统代填变成扩展直连

手册将用户验证作用在 http(s)/socks/mixed 代理上，`authentication` 列出用户名与密码；`skip-auth-prefixes` 给出可跳过验证的 IP 段，例如 `127.0.0.1/8` 与 `::1/128`。系统代理通常让浏览器连本机端口，来源落在回环前缀时可能跳过验证。扩展若填写局域网 IP、漏填账号，或连到未监听的地址，浏览器会立刻表现为能开、不能开或反复询问身份。判断依据：同一站点在关闭扩展时与开启扩展时，入站来源地址或是否触发验证不一致。

`allow-lan` 与 `bind-address` 进一步限制谁能连上端口。允许局域网为 true 时，其他设备可经代理端口访问互联网；绑定可以是全部地址或单个 IPv4、IPv6。扩展把主机写成网卡地址时，会受到 `lan-allowed-ips` 与 `lan-disallowed-ips` 约束，且黑名单优先。这会让只开扩展的浏览器和只走系统代理的浏览器看到不同连通性。

## 进核之后仍由运行模式决定走向

扩展只能改变流量是否进入 Clash，不能单独改写内核的 `mode`。`mode` 为 `rule` 时按规则匹配，为 `global` 时走全局代理并需要在 GLOBAL 策略组选择，为 `direct` 时全局直连，默认规则模式。因此出现开了扩展反而全部直连时，应先看 `mode` 是否为 `direct`，而不是假定扩展改写了规则。判断依据：扩展已连通入站，但出站行为与当前 `mode` 一致。

`find-process-mode` 为 `always`、`strict` 或 `off`。浏览器进程在强制匹配时可能套用进程规则；扩展改变的是套接字目标，进程名仍是浏览器。于是同一浏览器在系统代理进入内核和扩展连入内核两条路上，进程匹配结果可能相同，但若扩展连的根本不是 Clash，进程规则不会生效。判断依据：日志中能否看到该浏览器进程。

## 日志、IPv6 与失败时的解释顺序

`log-level` 控制控制台与控制页面输出：`debug` 尽量输出运行中所有信息，`info` 含一般运行内容，`warning` 与 `error` 更窄，`silent` 不输出。解释扩展为何改变行为时，应能在日志中看到新的入站；若没有，行为变化来自浏览器根本没连 Clash。`ipv6` 默认为 true，扩展若改用 IPv6 字面量主机，会走到与 IPv4 不同的接受条件。

失败时下一步：先用日志确认扩展是否产生了 Clash 入站；再核对验证与 `skip-auth-prefixes`；然后读 `mode` 是否把所有已进核流量变成直连或全局代理。不要把 `external-controller`、外部用户界面或 GEO 下载地址解释成浏览器行为来源。若关闭扩展后行为立刻回到与其他应用一致，即可判断差异来自扩展改写了入口，而不是路由规则文件本身。字段说明见全局配置文档。
