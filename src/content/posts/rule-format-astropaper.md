Clash 的 rules 列表按「规则类型、载荷、出站」解析，并不是可以把任意字符串贴到同一位置的备注。官方条目用逗号分隔：第一段选定匹配器，第二段必须是该匹配器认识的载荷，第三段才是命中后的策略。完整域名、后缀、关键字、通配、正则、Geosite 分类名、CIDR、ASN、国家代码、进程名、逻辑子规则、规则集合名，在说明里分属不同字段。把一种格式直接接到另一种类型后面，不是解析失败，就是按错误算法匹配，所以不同规则载荷格式不能直接混用。

## 类型怎样锁定载荷含义

域名族彼此也不可互换。`DOMAIN` 匹配完整域名；`DOMAIN-SUFFIX` 匹配后缀，例如 `google.com` 可匹配 `www.google.com`、`mail.google.com` 和 `google.com`，但不匹配 `content-google.com`；`DOMAIN-KEYWORD` 按关键字包含；`DOMAIN-WILDCARD` 仅支持星号与问号，且与配置文件其他地方的 Clash 格式通配符不相同；`DOMAIN-REGEX` 走正则。同一段主机名只能按所选类型解释，也不能拿去当作 `GEOSITE` 的分类名。

地址与归属同样拆开：`IP-CIDR` 与 `IP-CIDR6` 效果相同，后者只是别名，载荷必须是地址范围；`IP-SUFFIX` 匹配 IP 后缀；`IP-ASN` 匹配 ASN；`GEOIP` 匹配国家代码。来源侧使用 `SRC-GEOIP`、`SRC-IP-CIDR` 等独立类型。端口、入站、网络则有 `DST-PORT`、`IN-TYPE`、`NETWORK` 等。进程规则的载荷是路径或进程名，在 Android 上可以匹配包名。`RULE-SET` 的载荷是规则集合名称，需配置规则集合，不能把一条普通 `DOMAIN` 规则整行塞进该字段。

逻辑规则形式为类型后紧跟双层括号中的子条件，例如 `AND`、`OR`、`NOT`，payload 仍是「规则类型和其他 payload」，必须注意括号。`SUB-RULE` 同样要注意括号。`MATCH` 匹配所有请求，无需条件。内层缺少类型、少一层括号，都属于把普通载荷格式混进逻辑规则。

## 附加参数不能跨类型套用

`no-resolve` 仅支持关于目标 IP 的规则。域名开始匹配这类规则时，mihomo 将触发 DNS 解析以检查目标 IP 是否命中，可选该参数跳过解析。若更早的匹配已经触发过解析，则依旧会匹配到带该参数的目标 IP 规则。`src` 也仅支持目标 IP 规则，作用是把目标 IP 匹配转为来源 IP 匹配。这两项都不能当作所有规则的通用尾巴。

规则从上到下匹配，顶部优先。若请求为 UDP，而节点没有 UDP 支持（例如 ss 节点没写 udp 开启），则会继续向下匹配。看起来像「混用偶尔能用」，往往是没命中当前行而落到后面的规则，和载荷格式被正确解析不是一回事。

## 场景改写步骤与失败后的下一步

场景甲：清单是主机名，却写成了网段或国家代码。步骤如下：先看载荷形态；主机名在域名族里选择完整匹配或后缀匹配；Geosite 分类名只用 `GEOSITE`；只有确实要按解析后的地址段控制时，才使用 `IP-CIDR`，并判断要不要加 `no-resolve`。判断依据：有无 CIDR 斜线、是否为国家代码、是否为分类名而不是普通域名。

场景乙：要求域名与协议同时成立。步骤：不要把两种载荷写进同一条普通规则；写成逻辑规则，内层分别保留类型，官方示例为 `AND,((DOMAIN,baidu.com),(NETWORK,UDP)),DIRECT`，括号必须成对。判断依据：拆开内层后，每一段仍能识别为合法的类型加载荷。

场景丙：复用一批规则。步骤：在 rules 中只写规则集合引用，第二段用集合名，第三段给出站。判断依据：该行类型是 `RULE-SET`，载荷不是域名、也不是 CIDR。

失败后的下一步：对照类型列表确认第一段存在；用该类型示例核对第二段字符形态；逻辑与子规则只查括号和内层类型；附加参数仅保留在目标 IP 类规则上；若文件能加载但不按预期分流，再查是否被上方规则抢先命中，或 UDP 导致继续向下匹配。应当按类型改写载荷，而不是把不同格式拼接在同一条规则里。
