策略组上与延迟相关的数字，来自健康检查，不是通用的链路质量仪表。读它之前要按官方字段分清：这次测量覆盖哪些对象、以什么为成功，以及哪些问题根本不在这次检查里。把卡顿、UDP 成败或集合内节点状态都算进同一个数字，会超出资料给出的含义。

## 健康检查实际衡量什么

衡量的是：向该策略组 `url` 做健康检查时，能否在给定约束内得到可接受结果。`timeout` 给出等待上限，单位毫秒。若配置了 `expected-status`，则还衡量 HTTP 响应状态码是否落在允许集合内；可使用斜线匹配多个状态码，使用短横匹配状态范围，并可混合书写。资料中的示例包括匹配 `200/302`、匹配 `400-503`、以及 `200/302/400-503`。未配置时默认 `*`，对响应状态不做要求，此时重点是检查过程是否在时限内完成，而不是页面正文、证书品牌或下载速率。

`interval` 不为 0 时，上述衡量按秒级周期重复。`lazy` 为 true 时，未选择到当前策略组就不进行测试，等于这段时间没有新的测量。`max-failed-times` 把连续失败次数纳入是否触发一次强制健康检查的条件，默认 5。这些字段共同构成可用性探测，而不是转发路径上的逐包时延统计，也不是业务请求成功率统计。

## 明确不衡量、覆盖不到的对象

资料直接写明：`url` 只会检查代理组 `proxies` 字段的代理，不会检查代理集合里通过 `use` 引入的代理。组级延迟因此不代表集合内节点经历了同一过程。把 `use` 成员的快慢读成该组 `url` 的测量，已经超出字段定义。

`filter`、`exclude-filter`、`exclude-type` 只决定谁进入组。`exclude-type` 不支持正则，用竖线按类型排除引入的出站代理，无视大小写，它不产出延迟。`disable-udp` 只声明是否禁用该策略组的 UDP，健康检查字段没有把 UDP 连通写成探测指标。组级 `interface-name` 与 `routing-mark` 已弃用，延迟不能理解成「组级绑网或路由标记是否成功」的读数；出口相关项的优先级是代理节点大于代理策略大于全局。

资料也没有把带宽、丢包、视频首帧、规则命中次数列为健康检查输出。`hidden` 与 `icon` 只影响 API 返回的展示信息，不改变测量含义。`empty-fallback` 与 `default-selected` 处理空组和缺省选择：前者只支持 proxy 名称且不能填代理组，后者在名字不存在时选第一个节点，二者都不是延迟指标。

## 读结果时的判断依据与失败下一步

看到某成员的延迟或失败时，先问三件事：它是否位于该组 `proxies` 列表；当时是否因 `lazy` 被跳过而未测；`expected-status` 是否把「能连通但状态码不同」判成失败。若成员只出现在 `use` 的集合中，组上的延迟列不能当作对它的测量。若所有 `proxies` 成员同时失败，优先核对该 `url` 与 `expected-status` 是否同一套条件，而不是比较节点负载。定时不更新时，检查 `interval` 是否为 0。需要改出口网卡或路由标记时，到节点字段按优先级处理，不要用延迟数字反推已弃用的组级键。若目的只是比较谁该进组，应去改筛选表达式，那与健康检查不是同一项测量。仍无法解释时，回到代理组字段中关于 `url` 作用范围和期望状态的定义，而不是把未记载的业务指标补进延迟含义。
