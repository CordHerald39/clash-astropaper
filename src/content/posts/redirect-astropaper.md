订阅地址有两种常见答法：直接给出配置，或先发重定向再让客户端去另一个 URI。二者在 HTTP 里分属不同状态码类，不能用“最后都能打开”混为一谈。MDN 写明：200–299 表示请求成功完成，300–399 是重定向消息；成功的具体含义还取决于方法。对 GET，200 表示资源已获取并在消息体中传输；3xx 则是告诉客户端资源换了位置或应改用另一 URI，本身不保证当前响应体就是配置。

## 适用条件

适用于比较“同一订阅 URL 是直接 2xx 回配置，还是 3xx 再跳转”的场景，以便决定能否把响应体当配置解析、以及下次是否仍请求原 URL。依据是 RFC 9110 状态码；未列出的码可能是服务器自定义，不能归入标准的“直接成功”或“标准重定向”。本文不涉及具体客户端界面，只比较协议语义。

## 直接返回：看成功类如何交付资源

直接返回配置，判断依据是成功类且消息体可用：

- 200 且方法为 GET：资源在消息体中传输，这是“直接返回配置”最贴近标准的形态。HEAD 则只含表示头、没有消息体，不能当配置文本。
- 203：返回的元数据与源服务器不完全相同，来自本地或第三方副本，多用于镜像或备份。除该特定情况外，更推荐 200。若订阅走 203，应视为非权威副本，与源站直接 200 不是同一可信级别。
- 204：没有内容可发送，但头有用，用户代理可用新头更新缓存。没有消息体就谈不上直接返回配置。
- 304：用于缓存，表示响应未修改，客户端可继续使用同一份缓存。它不是“再传一份配置”，也不是迁址。

201 表示创建了新资源，202 表示已收到但尚未处理且 HTTP 无法稍后异步告知结果，二者都不是“把现成配置放在 GET 消息体里”。把它们当成导入成功，依据不足。

## 重定向：只给新 URI，且永久与临时、是否改方法都不同

重定向类的共同特点是：当前响应的职责是指引下一跳，而不是完成 GET 语义下的资源传输。

- 301：URL 永久改变，新 URL 在响应中给出。以后应以新 URL 为权威地址。
- 308：永久位于 Location 头中的另一 URI，语义同 301，但不得改变方法。
- 302：URI 临时改变，今后仍应使用原来的 URI 再请求。把 302 的落点存成“新的配置地址”，与规范相反。
- 307：临时改 URI，且必须用与先前相同的方法；若第一次是 POST，重定向后仍必须 POST。它与 302 的差别是方法约束，不是临时/永久。
- 303：要求用 GET 到另一 URI 取资源。即使最初不是 GET，下一跳也会变成 GET。这与“原样跟随并直接解析配置”不同，下一跳可能是说明页、登录页或其他文档。
- 300：多种可能响应，没有标准化自动选择方式，很少使用。客户端若自动挑了一个 URI，该选择没有标准算法背书。

305 已因带内配置代理的安全问题弃用；306 保留但不再使用。它们不属于可用的“跳转后再取配置”模型。

## 实务上如何并列比较、失败时怎么办

比较一次“直接返回”和一次“先重定向”时，应并列记录：最终是否出现 GET+200 且存在消息体；中间有几个 3xx；Location（或响应中给出的新 URL）是否改变主机；方法是否被 303 改成 GET，或被 307/308 要求保持。只有最后一跳满足 GET 成功并带消息体，才具备“拿到资源”的标准含义；此前的 3xx 只说明路径，不说明内容。

若只有 3xx 没有后续 2xx，配置并未按 GET 成功语义交付。若重定向后是 401/403，说明新 URI 需要认证或已明确无权限，与直接 200 回配置不同。404/410 表示没有可取资源，410 还要求清除缓存和链接。502/504 是网关问题，503 为暂时不可用，应把暂时条件与可缓存的成功响应区分开。出现循环时，508 表示检测到无限循环，应停止把跳转链当成有效交付。未列出的状态码不要折算成 200 或某一 3xx。
