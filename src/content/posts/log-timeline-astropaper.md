同一秒内出现多条 Clash 日志，并不能据此断定它们属于同一条连接。官方把日志定义为内核按级别输出的运行信息，位置只在控制台和控制页面；级别决定“这一秒里能看见多少类事件”，并不提供“同一秒等于同一连接”的分组规则。

## 适用条件与不能怎样推断

这一判断适用于：你在控制台或控制页面看到时间戳落在同一秒、于是想把这些行当成一次会话来分析。它不适用于：把 `debug` 或 `info` 下的密集输出直接等同于单连接的完整轨迹。

级别会改变同一秒内的行数。`debug` 尽可能输出运行中所有信息，同一秒出现多行是预期现象。`info` 会输出一般运行内容以及 error、warning，同一秒里完全可以既有一般运行、又有错误。`warning` 与 `error` 较窄，但只要内核在该秒处理了多件“出错”或“无法使用”的事，仍可并排出现。因此“同一秒”只说明观察粒度，不说明连接身份。

## 为何同一秒可以对应多件并发之事

全局配置里还有会在短时间内并行产生事件的选项，它们与日志级别叠加后，更容易在同一秒写出多行，且彼此不必是同一连接。

例如 `tcp-concurrent` 为 true 时，会使用 DNS 解析出的所有 IP 去连接，并采用第一个成功的连接。一次业务请求在内核侧可能对应多次出站尝试，这些尝试的日志若被当前级别收录，可以挤在同一秒，却不是“一条连接写了多行”这么简单。

`ipv6` 为 true（默认即为 true）时，内核接受 IPv6 流量，与 IPv4 相关事件可以交错出现。`mode` 为 `rule` 时走规则匹配，为 `global` 或 `direct` 时路径不同，但都不会把“同一秒的多行”绑定成同一连接。`find-process-mode` 在 `always` 或 `strict` 下还可能为进程匹配付出额外工作，这些同样是内核运行信息，级别够高时会进同一秒的输出。

判断依据：连接是否同一条，不能用秒级同时出现来证明；只能看该行内容是否在描述同一类错误，以及它属于 error、warning 还是仅仅是 info 的一般运行。官方并未把日志按连接编号成组，缺这个依据时不要自行合并。

## 读同一秒多行时的步骤与失败下一步

第一步，记下该秒前后你实际做了什么，以及当时的 `log-level`。若是 `debug`/`info`，先承认同一秒多行是级别特性，而不是连接合并的证据。

第二步，按级别拆行：一般运行内容（info）与“不影响运行的错误”（warning）、“错误至无法使用”（error）分列。同一秒内三类可以共存，合并成“一条连接的故事”会误判。

第三步，若开启了 `tcp-concurrent`，把“多次 IP 尝试、取第一次成功”考虑进去：同一秒的多条出站相关输出，更可能是并发尝试，而不是单连接重复。

若仍把同一秒多行当成同一连接且结论互相矛盾：把 `log-level` 降到 `error` 或 `warning` 后只触发一次操作。若降级后同一秒仍有多条 error，说明该秒内确实发生了多起“无法使用”级事件，应视为多事件并列，而不是强行合成一连。若降级后同一秒只剩一行或没有错误行，则原先多行主要来自一般运行或 debug 细节，更不能当作同一连接的证据。
