把负载均衡策略组理解成一次下载把多条线路的带宽叠加上去，与官方代理组通用字段所描述的对象不一致。该页说明的是：策略组如何引入出站、如何排序、如何用 HTTP 探测判断节点是否可用。它没有把策略组定义成把多条出站合并为同一条传输的带宽聚合器。适用条件：你的问题是单次下载没有变快，或速度不是多条线路之和。此时应把目标限制在从候选里选择出站，并用下面的字段做判断。

## 文档在定义可用性，而不是定义吞吐叠加

健康检查字段全部指向探活，没有指向测速或带宽相加。`url` 是健康检查测试地址；`timeout` 是探测超时毫秒；`interval` 是间隔秒，非 0 才定时测；`lazy` 默认 true，组未被选中时不测；`expected-status` 用 HTTP 响应状态码判断可用，默认星号不做要求；`max-failed-times` 超过则强制再测，默认 5。判断依据：这些参数的输入是测试地址与状态码，输出是节点是否可用，中间没有把多个节点的带宽加总的字段。若一次下载变快或变慢，不能用该页的通用字段证明是叠加成功或失败。

`expected-status` 的写法也说明判定粒度是状态码：可用斜线匹配多个码，用短横匹配范围，例如 200 与 302、400 到 503，或混合。这是可用性开关，不是带宽权重。场景步骤：先读出该组是否配置了期望状态码，再确认探测响应是否落在该范围内，最后只把结论写成某节点可用或不可用，不要写成带宽被合并或未被合并。

## 策略组维护的是候选集合与选择回退

`proxies` 引入出站代理或其他策略组，`use` 引入代理集合。`include-all` 等字段按名称排序纳入节点。`default-selected` 指定默认节点，空或不存在则用组中第一个节点。`empty-fallback` 在组为空时回退到某个 proxy 名，默认 `COMPATIBLE`，且不支持填代理组。这些规则回答流量可以落到谁身上、没人可用时去哪，不回答同一条下载是否同时使用名单里所有人。

另外，组级 `url` 只会检查 `proxies` 里的代理，不会检查 `use` 引入的代理集合节点。即便有人把负载均衡理解成所有成员一起传，官方检查范围也并未覆盖 use 侧成员。把没看到带宽叠加归因于测试地址，首先就查错了层：测试地址不测量带宽，也不聚合带宽。`filter`、`exclude-filter`、`exclude-type` 只会增减成员。`disable-udp` 只关闭该组 UDP。`hidden`、`icon` 服务于 api 展示。它们都不能解释为叠加开关。

## 误判时如何纠正，失败时下一步

纠正步骤：第一，把目标改写为请求从组内某个出站离开，而不是组把带宽相加。第二，核对最终成员列表及排序，确认你以为在共同传数据的节点确实仍在集合中。第三，若在观察节点是否可用，只把 `url`、`expected-status`、`timeout`、`interval`、`lazy` 当作探活工具。第四，若成员来自 `use`，不要用组级健康检查解释这些成员的容量或可用性。

失败时下一步：单次传输仍只表现一条出站特征时，回到 `type`、`proxies` 或 `use` 与 `default-selected`，确认选择发生在组这一层。若节点频繁消失，查 `expected-status` 是否与探测响应不一致，或 `max-failed-times` 触发了强制检查。若组为空，查 `empty-fallback` 是否误填策略组。出站网卡或路由标记不要写在已弃用的组级 `interface-name`、`routing-mark` 上，应写在节点上，优先级为代理节点大于代理策略大于全局。官方通用字段能够证明的是引入、排序与探活，不能用来保证任何带宽相加效果。
