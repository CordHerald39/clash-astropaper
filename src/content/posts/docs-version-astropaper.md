Clash 电脑端当前文档与旧版本功能对不上，通常不是同一功能简单改了名字。Clash Verge Rev 按标签发布，仓库把发行通道分成 Stable、已废弃 Alpha 与 AutoBuild；每个标签的说明列出当次修复与优化，并按 Windows、macOS、Linux 分行。文档若固定在某一旧标签或未标明通道，和本机当前安装对比时，就会在功能有无、前提条件、执行顺序上出现差别。

## 适用条件

适用：你同时看到一份较新的说明（仓库或当前发布页）和一份旧教程或旧标签说明，并发现步骤、限制或结果对不上。不适用：未核对标签就断言文档错误；把 AutoBuild 的缺陷当成 Stable 的正式行为；把其他图形界面的历史功能算进本项目。

判断依据：仓库要求到发布页下载对应安装包；“我应当怎样选择发行版”写明 Stable 高可靠性、适合日常使用，Alpha 已废弃，AutoBuild 滚动更新、可能存在缺陷。功能列表包括 mihomo 内核、可切换 Alpha 内核、Merge 与 Script、系统代理、TUN、可视化编辑、WebDav。这些条目会随标签修改变更边界，旧文档不会自动同步。

## 版本通道与平台支持造成的差异

旧文档若写于仍讨论 Alpha 通道，或写于未声明 Windows 对 Win7 停止支持之前，当前发布页已写明 Windows 不再支持 Win7，Alpha 标记为废弃。继续按旧文档在 Win7 或不支持的架构上操作，会得到与当前文档完全不同的能否安装、能否运行的结论。这是支持范围变化，不是某一参数写错。

平台包名也在变化。同一标签下 Windows 有 x64、arm64，以及仅在企业版或无法安装 webview2 时使用的 `fixed_webview2` 包；macOS 分 Apple M 的 aarch64 与 Intel 的 x64；Linux 分 deb 与 rpm 及 amd64、arm64、armhf。旧文档若只给一种包名，当前文档列出的变体更多。选错变体时，功能表现会与旧描述不一致，这往往是运行前提变了，而不是内核字段本身改名。macOS 要求 11+。旧环境低于该要求时，当前文档中的服务模式、TUN、系统代理相关描述不适用。

## 同一功能在相邻标签中被改过的边界

阅读 https://github.com/clash-verge-rev/clash-verge-rev/releases 上相邻版本可以看到，即便主版本仍是 2.5.x，行为边界也在变。例如：服务模式日志改为保存到文件以便追查内核被停止的原因；升级后服务版本或协议不兼容时提示重新安装；DNS 覆写改为按订阅独立记忆；扩展配置与脚本编辑会提示作用范围、执行顺序及应用设置优先级；由应用设置接管的字段若被扩展配置写入则丢弃并记日志。

旧文档可能仍假设 DNS 覆写全局有效且重启后保持，Merge 覆写 DNS 时旧条目自然消失，服务装好即可、无需考虑协议版本，扩展脚本写入的字段一定生效。当前说明已经改变这些前提。判断“文档与旧版不同”的依据是：在旧标签与新标签的说明正文中能否找到针对同一主题的修复或优化条目；能找到则属于已变更行为，而不是操作失误。

内核方面，仓库写明内置 Clash.Meta(mihomo) 并可切换 Alpha 版本内核。旧文档若针对另一内核或未切换内核的状态，节点、规则、DNS 字段的可用集合可以不同。应以本机实际内核与当前标签说明为准。仓库入口见 https://github.com/clash-verge-rev/clash-verge-rev 。

## 失败时如何处理文档冲突

两份文档都未写标签：都不可作为本机依据，回到仓库说明与当前 Stable 发布说明。旧文档能对应到明确标签、本机较新：从该标签向后读到本机标签，列出服务、TUN、DNS、Merge、Script、订阅缓存等相关变更，把旧步骤中被新说明取代的部分划掉。本机较旧、当前文档较新：不要用新文档的字段要求旧安装包；到发布页核对旧标签是否仍提供对应安装包，或先升级到文档所用的 Stable 标签再比较功能。通道混用时，AutoBuild 可能存在缺陷，其现象不能用来否定 Stable 文档，也不能用来证明旧文档仍然正确。
