讨论 URL 测试延迟和网页完整加载时间是否能互相换算时，只能使用手册对健康检查的定义。url 是健康检查测试地址；timeout 单位毫秒；interval 单位秒；expected-status 是期望的 HTTP 响应状态码。手册没有定义浏览器从请求文档到子资源全部结束的时间。二者不是同一指标。下面给出适用边界、差别的判断依据，以及把两种时间混用失败后如何回到字段。

## 手册里的 URL 测试指什么

适用前提是策略组填写了 url，并且你所说的延迟来自该健康检查。检查对象仅限 proxies 中的代理，通过 use 引入的代理集合不会被检查。lazy 默认为 true，未选择到当前策略组时不进行测试，此时没有新样本。interval 不为 0 才定时测试。expected-status 默认为星号，对状态不做要求；配置后只有状态码与期望一致才认为可用。状态码可用斜线匹配多个值，用短横线匹配范围，可混合，例如 200/302、400-503、200/302/400-503。timeout 只约束这次探测过多久算失败。以上就是该页上 URL 测试的边界：一次指向检查地址的 HTTP 探测、可选状态码比对、超时和周期。name 与 type 必须存在，含特殊符号的名称应当加引号，否则你甚至无法确认数字属于哪一个组。max-failed-times 默认 5，超过才强制健康检查，它改变的是何时重测，不是指标含义。

## 与网页完整加载的差别

网页完整加载通常包括文档、重定向、样式、脚本、媒体以及页面随后发出的接口，可能出现多种状态码和多条连接。手册中的健康检查不描述这些步骤。差别按判断依据拆开。第一，目标不同：url 指向健康检查测试地址，示例为 generate_204 一类探测，不是首页完整文档树。第二，成功标准不同：检查可以在默认星号下忽略状态码，也可以在填写 expected-status 后只认列出的码；完整加载还会关心子资源是否成功、是否还要执行脚本。第三，时间窗口不同：timeout 的毫秒是探测放弃点，不是页面收齐所有子资源的终点。第四，样本范围不同：只有 proxies 里的出站被检查，集合里的成员即使实际在打开网页，也不进入该组 url 统计。第五，是否执行不同：未选中且保持默认懒惰时根本不测，而网页加载发生在实际被选中的链路上。因此把检查延迟写成打开网页要多久，缺少该页依据。filter 改变谁被测，也不改变指标定义。

对阅读配置的人来说，判断自己有没有把两种时间弄混，可以用三个问题：这次数字是否声明来自 url 健康检查；被测出站是否在 proxies 而不是仅在 use；当时组是否因 lazy 被跳过。三个问题里任一为否，数字就不能拿去代表网页完整加载。expected-status 即使写成 200/302/400-503，也只是在探测响应码层面做集合匹配，不会统计页面里每一个资源的耗时，更不会把脚本执行算进去。interval 让检查按秒周期重复，页面加载却是一次性用户操作。官方资料能支持的结论只有：URL 测试是带可选状态码约束的 HTTP 健康检查；网页完整加载时间不在该页定义之内。

## 混用失败时下一步

若用 URL 测试延迟解释页面快慢并出现矛盾，下一步把指标拆回字段。先确认数字是否来自已启用的健康检查：url 是否存在、interval 是否非 0、组是否因 lazy 被跳过。再确认被比较的出站是否在 proxies 中。然后单独看待 expected-status：状态符合只说明探测响应码可接受，不说明其余请求耗时。timeout 到期只说明这次探测失败。不要在配置中寻找本页没有的完整加载时间字段。default-selected、empty-fallback、hidden、icon、disable-udp 以及已弃用的出站接口和路由标记，都不参与两种时间的换算。若希望检查更接近页面是否可访问，只能在允许范围内改 url 与 expected-status，并接受它仍然只是一次 HTTP 健康检查。include 类开关只改变成员名单与排序，不把探测升级成整页计时。
