代理集合上的 health-check 在文档中写作健康检查，并注明为延迟测试。因此一次结果首先说明的是：在给定的检查地址、间隔、超时和期望状态下，该节点是否完成了一次延迟测试。它不说明集合有没有下载成功，也不说明筛选正则有没有写对。适用条件是 enable 为 true；当 lazy 为 true 时，还要求该集合节点正处于使用中，否则按文档不测。读结果时必须把“未测试”“超时”“状态不符”分开，否则会把连接情况说错。

## 结果能够说明的连接情况

当测试实际发出时，结果只和这些条件绑定：是否在 timeout（毫秒）内结束；响应状态是否满足 expected-status；由此得到延迟测试层面的通断与时延信息。检查地址决定探测打到哪里，与集合用于下载的 url 无关。检查间隔（秒）只决定多久测一次，不决定单次成功还是失败。判断依据应同时写清检查地址、超时、期望状态和间隔。缺了超时，无法区分“仍在等待”和“已经放弃”。缺了期望状态，无法解释“有响应却仍算失败”。缺了是否正在使用该集合，无法解释懒惰状态下为什么完全没有数字。文档把这项机制定义为延迟测试，所以结果能够说明的是本次探测是否按上述条件完成，而不是长期稳定性。

## 结果不能说明的情况

lazy 默认为 true 时，不使用该集合节点就不会测试，没有结果不能说明连接失败，只能说明测试未发出。filter、exclude-filter、exclude-type 改变谁进入集合，检查结果不能用来反推名称正则或类型排除是否正确。更新集合的 interval、下载用 proxy、size-limit、header、path 只作用于获取文件；一次延迟测试的成败，不能证明这些下载参数正确或错误。override 里的名称前后缀、名称替换以及各类通用字段覆写，也不由健康检查验证。文档没有把健康检查等同于带宽、容量或持久可用证明，因此不能根据一次结果去保证传输表现。若集合其实是靠 payload 在解析失败后顶上的备用内容，检查结果同样只反映这些备用节点的延迟测试，不反映原先 http 或 file 为什么解析失败。

## 依据结果决定下一步时怎样表述

若结果为超时：下一步核对 timeout 是否误把毫秒当成秒，检查地址是否写在 health-check.url，并确认测试时集合确实在用。若有响应但未通过：对照 expected-status 是否与该检查地址的预期一致。若完全没有结果：先看 enable 与 lazy，再看筛选后是否还有节点。若集合加载正常、只有个别节点无结果：把问题留在延迟测试层，不要改 type，也不要为此改 payload。对外说明时应写成“延迟测试在某超时与期望状态下未完成或未匹配”，不要写成下载失败或筛选失败。需要他人理解这次结果时，必须连同检查地址、间隔、超时、lazy 和 expected-status 一起给出，否则无法判断当时测到的是哪一种连接情况，也无法判断有没有被懒惰状态跳过。
