打开一个网页时，浏览器会请求页面主机名，也会请求脚本、图片、接口使用的其他主机名。Clash 的路由按每一条请求独立匹配 `rules`，官方规则类型里没有“主域名一旦命中、子资源自动跟随”的写法。因此主文档给出的完整域名、后缀、关键字、GEOSITE 和 IP 类规则，会让主站与资源站走不同出站。下面只说明这种差异为什么会出现，以及如何判断。

## 适用条件

适用于阅读 mihomo 路由规则、需要理解“页面主机名与资源主机名可能被分开处理”的场景。依据是官方列出的 `DOMAIN`、`DOMAIN-SUFFIX`、`DOMAIN-KEYWORD`、`DOMAIN-WILDCARD`、`DOMAIN-REGEX`、`GEOSITE`，以及 `IP-CIDR`、`GEOIP`、`NETWORK`、`DST-PORT` 和 `MATCH`。不把某个具体网页的资源清单当作配置事实。

## 不同规则类型覆盖的主机名范围不同

`DOMAIN` 只匹配完整域名。主站若是带前缀的主机名，写成另一条不含前缀的 `DOMAIN` 既不会匹配主站，也不会匹配 CDN 或第三方资源域。`DOMAIN-SUFFIX` 按后缀匹配：文档示例中，`google.com` 可匹配 `www.google.com`、`mail.google.com` 和 `google.com`，但不匹配 `content-google.com`。同后缀的 CDN 可能和主站一起命中；名称里只是含有相近字段、后缀却不同的资源域名不会命中。资源主机名经常是另一个注册域，既不是主站子域，也不能写进同一条后缀规则。

`DOMAIN-KEYWORD` 只看关键字是否出现在当前请求的域名里。主站与资源站共享关键字时会被同一条规则带走，不共享则完全分开。`DOMAIN-WILDCARD` 仅支持 `*` 和 `?`，`*` 匹配零个或多个字符，`?` 匹配一个字符，且与配置文件其他地方的 Clash 格式通配符不相同。写在主站上的通配，覆盖不到另一资源域。`DOMAIN-REGEX` 同样只作用于当前请求的域名字符串。`GEOSITE` 匹配 Geosite 内的域名，部分内容参考 v2fly/domain-list-community；主站分类与资源站分类可以不同，从而进入不同出站。

## 每条资源请求独立匹配且受优先级约束

规则从上到下匹配，顶部优先。主站请求可能命中靠前的 `DOMAIN` 或 `GEOSITE` 并走某一出站；随后一条资源请求若先命中更靠上的关键字、`GEOIP` 或 `IP-CIDR`，会使用另一出站。`MATCH` 匹配所有请求、无需条件，未单独写出的资源域名会落到 `MATCH` 指定策略。因此“主域名已经写进规则”不能推出资源域名走同一策略。

目标 IP 类规则在匹配时会触发 DNS 解析，以检查域名的目标 IP 是否匹配；可以选择 `no-resolve` 跳过解析。如在更早的匹配中触发了 DNS 解析，则依旧会匹配到添加了 `no-resolve` 的目标 IP 类规则。主站与资源站解析到不同国家或不同网段时，`GEOIP`、`IP-CIDR`、`IP-CIDR6`、`IP-ASN`、`IP-SUFFIX` 会给出不同结果。这是同一页面里路由分裂的另一原因。`NETWORK` 可区分 tcp 或者 udp，`DST-PORT` 区分端口。文档还说明：请求为 udp 而代理节点没有 udp 支持（例如 ss 节点没写 `udp: true`）时，会继续向下匹配，故实时类资源可能与主文档的 TCP 请求不一致。

逻辑规则 `AND`、`OR`、`NOT` 组合的是单次请求的条件，例如域名加网络类型，不会把整页所有主机绑成一次匹配，并需要注意括号。`RULE-SET` 引用规则集合时，集合内对资源域名的条目同样独立生效，需配置 rule-providers。

## 判断依据与失败时下一步

判断主域与资源域是否被分开处理，应分别列出页面主机名和实际资源主机名，从上到下模拟它们各自命中的第一条规则，而不是只看主域那一行。若资源主机名更长、后缀不同或属于另一 `GEOSITE`，说明规则类型本身就会把它们分开，需要为资源主机名补 `DOMAIN`、`DOMAIN-SUFFIX` 或 `GEOSITE`，或接受其落入 `MATCH`。若补齐域名规则后资源仍异常，再查该资源是否命中 `REJECT`、错误的 `GEOIP`/`IP-CIDR`，或 udp 继续向下匹配。不要把“主站规则已存在”当成资源请求的命中依据。进程类规则只按发起进程分流，不能把不同主机名合并为一次匹配。
