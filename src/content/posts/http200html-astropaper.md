在 HTTP 里，「请求成功」有明确边界。MDN 写明：状态码表示某次 HTTP 请求是否已成功完成；2xx 是成功响应。成功并不等于应用层对象正确。Clash 要的是一份可解析的配置，而状态码只描述传输结果。把两者当成一回事，就会在 200 之后仍然得到无法使用的内容。

## 适用条件

适用于需要解释「日志显示成功、配置却不可用」的场景，以及制定「何时才能相信这次更新」的判断标准。不适用于尚无状态码的失败，也不适用于把 4xx、5xx 说成成功。1xx 只是中间过程，例如 100 表示可以继续请求，同样不代表配置已正确。

## 原理与判断依据

1. 成功的含义随方法变化。GET 的 200 表示资源已取出并放在正文里；HEAD 的 200 只包含表示头、没有正文；PUT 或 POST 的 200 正文描述的是操作结果；TRACE 的正文是服务器收到的请求本身。订阅场景若实际发出的不是 GET，即使 200，正文也可能根本不是配置文档。
2. 2xx 内部并不都表示「配置已到手」。204 明确没有正文。202 表示已接收但尚未处理，HTTP 没有稍后补发最终结果的标准通道。206 只满足范围请求的一部分。203 的元数据可以来自本地或第三方副本。这些都是成功类响应，却都不保证能得到完整、权威、可解析的配置。
3. 3xx 会改变你拿到的是哪一份资源。301、308 永久换位置；302、307 临时换位置；303 让客户端用 GET 另取。客户端若跟随跳转，成功取到的是新 URI 上的表示，可能是登录页或说明页。304 告诉你可以继续用缓存，缓存错误时「成功」会复用错误内容。
4. 4xx、5xx 更不能外推成内容正确。401 要求客户端先完成认证；403 是已知身份仍拒绝给出资源；404 找不到；410 永久删除；429 是短时间请求过多；500 是找不到更合适 5xx 时的通用服务器错误；502、504 是网关拿到无效上游或等待超时。它们都表示这次没有成功取出你要的资源。

判断依据：只有在方法符合预期、最终 2xx 且不是 202、204、206 这类「成功但没有完整目标正文」、也没有跳转到其它文档、也不是 304 误用缓存时，才具备「内容可能正确」的 HTTP 前提。内容是否真能解析，仍要在应用层验证。

## 失败时下一步

若只有「成功」二字没有三位码，补记状态码再套用上面的分类。若是 200 但内容不对，按跳转、方法和 2xx 细分排查，而不是反复重试网络。若是 4xx 或 5xx，先处理认证、权限、资源存在性或网关，不要进入配置语法检查。未在 RFC 9110 列表中的数字按非标准响应记录，不要自行映射成 200。
