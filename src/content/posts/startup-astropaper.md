开机启动说的是：登录或开机之后，Clash Verge Rev 这个图形客户端进程是否被系统拉起来。代理服务就绪说的是：内置的 Clash.Meta(mihomo) 内核已经在运行，并且你所依赖的系统代理或 TUN 已经处于可用状态。仓库把它定位为基于 Tauri 的 Clash Meta 图形界面，功能列表同时写了系统代理（含守卫）和 TUN。发布说明则表明：应用启动成功、内核启动成功、TUN 可用、系统代理状态可读且端口有效，并不是同一件事。

## 适用条件

适用于 Clash Verge Rev 电脑端，需要解释「开机后看到客户端」与「这时流量已经被正确代理」为何经常不一致。支持的系统见项目说明：Windows、Linux 与 macOS 11+；Windows 安装包发布说明写明不再支持 Win7。若使用开发命令 `pnpm dev`，它会保留开发通道里服务是否安装的状态，未安装则走 Sidecar。这只能说明开发环境，不能用来定义日常开机启动是否等于服务就绪。

## 两套状态如何区分

开机启动只覆盖图形进程。只要客户端已经出现，就可以说「启动了」。它不保证内核在。发布说明曾修复「内核未运行时，首页仍显示服务模式」，判断依据因此不能是首页上的模式标签，而应是内核是否真正在跑。

代理服务就绪至少包含：内核由服务模式或 Sidecar 之一成功拉起；若走系统代理，系统里的代理设置指向当前内核仍在监听的端口；若走 TUN，虚拟网卡可用。发布说明把下列现象写成相互独立的故障：服务模式内核无法启动、TUN 不可用、系统代理状态读取报错、内核意外停止后系统代理仍指向失效端口。判断依据：其中任何一项失败，都属于客户端也许已开机启动，但代理服务未就绪。

时序也不同。开机启动可以发生在网络尚未就绪时；代理服务就绪依赖当时的网络与权限。macOS 发布说明写明：VPN 接管网络或开机网络未就绪时，服务模式内核无法启动、TUN 不可用、系统代理状态读取报错。也就是说，开机启动动作已经发生，代理服务仍可能因为网络未就绪而没有就绪。Windows 上服务已停止时，还曾出现启动后约两分钟才出窗口，窗口出现时间也不能当成内核就绪时间。

服务与 Sidecar 是两条就绪路径。仓库用 `pnpm dev:service` 与 `pnpm dev:sidecar` 区分「安装或更新服务」和「无特权 Sidecar」。发布说明中大量故障发生在服务模式：权限误判、数据目录所有权、残留服务、服务版本不兼容。判断依据：开机启动成功只说明 GUI 起来了；服务就绪必须明确当前走的是服务拉内核还是 Sidecar 拉内核，并且该路径下内核没有退出。

## 启动了但未就绪时下一步

不要用反复开关开机启动来代替检查内核。先看启动失败或内核停止的具体原因。发布说明优化了这些提示，并让服务运行日志落到文件，便于追查内核被停止的原因。若系统代理还指向失效端口，应视为代理服务已离开就绪态，即使客户端仍在运行。

配置在重启后的变化也不等于开机启动失败。例如发布说明修复过订阅含自定义 DNS 时，已开启的 DNS 覆写在重启应用后被自动关闭。这属于内核已起来但行为与上次会话不同，应归入「服务是否按你预期就绪」，而不是「客户端有没有开机启动」。

若提示需要重新安装服务、或误报「需要更新系统服务」，按发布说明区分：后者在 macOS 上可以是偶发内核启动失败的误提示。首次管理员启动导致目录所有权不符、重装服务后内核缺失无法继续 Sidecar、Linux 上安装服务后仍不能开 TUN，都属于启动路径存在、就绪失败。只有内核在跑，并且系统代理或 TUN 与当前内核一致，才能说代理服务就绪；开机启动本身不蕴含这一结论。
