## 应用安装只负责把客户端放到本机

Clash 电脑端（macOS）的“安装”指：从官方 Release 取得与芯片匹配的 dmg（Apple 芯片为 `aarch64`，Intel 为 `x64`），把应用放到本机，使图形界面可以启动。仓库写明支持 macOS 11+（Intel/Apple），并要求到发布页下载对应安装包。这一步解决的是“有没有正确的客户端进程”，不解决“流量是否被系统代理或虚拟网卡接管”。

因此，dmg 拷贝完成、图标能出现，只能说明安装包架构和系统版本可能已经对齐。它不证明服务模式已安装，也不证明 TUN 可用，更不证明系统代理指向的是正在监听的端口。把“已经装上”理解成“网络权限已经齐”，会把后续的服务修复、内核启动失败误判成安装失败。安装说明与常见问题，仓库指向文档页；安装包选型本身仍以 Release 资产列表为准。

## 网络相关能力是另一层：系统代理、TUN、服务模式

官方功能说明把系统代理（及守卫）与 `TUN(虚拟网卡)` 模式单独列出。它们依赖内核处于可运行状态，并且在服务模式或 Sidecar 等运行方式下，权限边界不同。发布说明多次把“服务能否启动内核”与“TUN 是否可用”“系统代理状态能否读取”分开写，说明这是安装之后的运行时能力，不是 dmg 自带的一次性授权。

适用条件可以这样划分：只需要图形界面管理配置、且内核能在当前用户权限下拉起时，问题仍偏安装与来源；一旦要让系统代理生效、或让 TUN 接管流量，就进入服务/内核/网卡状态的范围。v2.5.7 写明：VPN 接管网络或开机网络未就绪时，可能出现服务模式内核无法启动、TUN 不可用、系统代理状态读取报错；用 `ipconfig set` 手动配置网卡后，可能无法设置系统代理。这些都是网络栈与服务时机问题，不能用“重新拖一次 dmg”代替。

v2.5.6 还写明：服务模式内核意外停止后，系统代理仍可能指向失效端口，从而无法上网。可见系统代理是“指向某个端口”的系统级设置，并不保证内核还在。用户目录在外置磁盘时，服务可能拒绝启动内核——这是服务对数据目录位置的检查，同样不属于“应用有没有装上”。

## 二者冲突时如何判断，以及失败后下一步

判断顺序建议固定为：先确认安装包来自 Stable 对应架构，应用能启动；再看内核是否在服务模式或 Sidecar 下真正运行；最后才看系统代理与 TUN。界面能开但 TUN 不可用，优先查服务、开机时网络是否就绪、是否另有 VPN 接管，而不是重装同一 dmg。能开但浏览器不通，优先查系统代理是否指向已失效端口，而不是先改订阅正文。

失败时：安装阶段对不上，回到 Release 重选 `aarch64`/`x64` dmg，不要用 Windows/Linux 包。内核或服务起不来，按该版本发布说明处理残留服务进程、用户组解析失败、数据目录位置，而不是反复开关代理。系统代理或 TUN 报错，把问题记在“网络权限/服务时机”上：等网络就绪后再启内核，避免在手动改过网卡配置的前提下强行写系统代理。安装完成只说明客户端在，网络权限要另核。
