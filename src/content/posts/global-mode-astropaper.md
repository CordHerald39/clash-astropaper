全局模式只影响已经进入 Clash 处理路径的流量，是因为官方把 `mode` 放在“运行模式”里，而不是放在“劫持系统全部套接字”的位置。资料对三项取值的说明是：`rule` 规则匹配，`global` 全局代理（需要在 GLOBAL 策略组选择代理或策略），`direct` 全局直连；该项有默认值，默认为规则模式。运行模式回答的是：内核在已经拿到一条连接之后，用规则表决策、统一交给 GLOBAL，还是统一直连。它不回答：这条连接当初是怎么到达代理端口的。未进入 http(s)/socks/mixed 等代理端口、被绑定地址拒绝、被认证拒绝、或因 IPv6 开关未被内核接受的流量，都不在 `mode` 的作用范围内。

## 运行模式与入站条件是两层配置

适用条件：你已经把 `mode` 设为 `global`，并观察到只有走 Clash 代理端口的程序发生了变化，系统里其他程序仍直连。判断依据就是本页把“允许局域网”“绑定地址”“用户验证”与“运行模式”分成不同小节。前者决定谁能经过 Clash 的代理端口访问互联网，后者决定进来之后怎么选路。

具体操作时先看入站字段。`allow-lan` 为 true/false，控制其他设备能否使用代理端口。`bind-address` 可为 `*`、单个 IPv4 或单个 IPv6。`lan-allowed-ips` 仅在允许局域网时生效，默认包含 `0.0.0.0/0` 与 `::/0`；`lan-disallowed-ips` 为黑名单且优先级更高。`authentication` 给代理端口加用户验证，`skip-auth-prefixes` 指定可跳过验证的前缀。这些条件任一不满足，连接不会成为“已被接管的流量”，`global` 对它没有意义。`ipv6` 决定内核是否接受 IPv6 流量，默认 true，这是另一条能否被接管的门槛。

## 进程匹配不负责扩大接管范围

有人会把“全局”理解成“所有进程强制匹配”。官方进程匹配模式并不等于运行模式。`find-process-mode` 可选 `always`（开启，强制匹配所有进程）、`strict`（默认，由 Clash 判断是否开启）、`off`（不匹配进程，推荐在路由器上使用）。它只控制内核要不要去匹配进程，方便规则或日志按进程理解连接，并不把未指向代理端口的套接字强行拉进 Clash。

因此，路由器或网关场景即使 `mode: global`，资料仍推荐可以 `off` 掉进程匹配：此时全局代理仍然只作用于已经转发到 Clash 入站的流量。桌面场景若设为 `always`，也只是对已接管连接补全进程信息，不能单独作为“系统全局劫持”的依据。判断时把两个字段拆开：`mode` 管出站决策模板，`find-process-mode` 管进程元数据是否收集。

## 需要对外观察时如何避免误判

若要用日志证明“只影响已接管流量”，应调整 `log-level`。`silent` 不输出，无法证明任何路径；`error`/`warning` 偏故障；`info` 含一般运行内容；`debug` 尽可能输出运行中所有信息。能在日志中出现的连接，才是内核已经处理的对象。未出现的连接，应回到绑定地址、认证、IP 段和 IPv6，而不是认为 `global` 失效。

通过 API 核对时，`external-controller` 提供 RESTful 控制，`secret` 为访问密钥。资料提醒：Unix socket、Windows namedpipe 访问 API 不验证 secret，API 上的 DOH 路径也不验证 secret。这些接口用于读 `mode`、读策略组选择（配合 `profile.store-selected` 是否储存 API 选择）时，只能说明内核内部状态，不能证明某应用已经把流量交给代理端口。失败时的下一步是：用入站字段确认该应用或该设备是否被允许连接代理端口；确认 GLOBAL 组已按官方要求完成选择；再用日志看该连接是否出现。三者同时成立，全局模式才会在这条已接管流量上表现为统一走所选代理或策略。
