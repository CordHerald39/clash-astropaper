在代理集合配置里，筛选节点和测速选择节点不是同一层动作，也不能互相代替。筛选回答的是哪些出站名称或协议类型可以进入该集合；测速回答的是进入集合之后，延迟测试会不会发出、在多长时间内结束、响应是否符合期望。官方把前者写成 filter、exclude-filter、exclude-type，把后者写成 health-check，并注明健康检查即延迟测试。适用条件是：已经配置 proxy-providers，类型为 http、file 或 inline，并且需要同时解释“名单为什么是这些节点”和“为什么有的节点没有延迟数据”。下面只说明这一区别、对应判断依据以及失败后的下一步，不补充图形界面名称，也不对时延高低作保证。

## 筛选只依据名称与类型

filter 用于留下满足关键词或正则表达式的节点，多个正则可以用反引号区分。exclude-filter 用同样规则做排除。exclude-type 不支持正则，只用竖线分割类型名，并按配置里的 type 字段排除。文档示例里，filter 使用了包含港、hk 等字样且带忽略大小写标志的表达式，exclude-type 示例则按 ss 与 http 排除。判断依据只有：节点名称是否命中表达式、节点 type 是否落在排除列表中。延迟数值、响应状态、检查地址都不参与筛选。因此，某节点不会因为后来测速完成而重新进入已被正则丢掉的名单，也不会因为启用健康检查而绕过 exclude-type。当名单偏多或偏少时，应先核对这些字段是否写在对应的集合名称下、正则是过宽还是过窄、类型字符串是否与配置中的 type 一致。

## 测速选择对应健康检查字段

health-check.enable 为是否启用延迟测试。health-check.url 是检查地址，不是集合下载地址。health-check.interval 是检查间隔，单位为秒。health-check.timeout 是超时，单位为毫秒。lazy 默认为 true，表示不使用该集合节点时不进行测试。expected-status 用于对照期望状态。判断依据是：在启用且未被懒惰状态跳过的前提下，测试是否发出、是否在超时时间内完成、状态是否符合期望，从而得到延迟测试层面的信息。这与名称里有没有地区字样无关。若未启用、或懒惰状态为真且当前没有使用该集合，就不会出现新的测速结果，不能据此认为筛选规则失效，也不能把“没有数字”写成“节点已被筛选删掉”。

## 具体场景中如何选择以及失败时下一步

只想保留名称含特定字样的节点时，应改 filter 或 exclude-filter，不要指望健康检查替你删名字。只想知道已进入集合的节点延迟测试有没有完成时，应查 enable、lazy、检查间隔、超时和期望状态。名单已经符合预期却完全没有延迟数据时，若 lazy 为 true 且集合未被使用，按文档不会测试，应先确认使用关系，再查超时与期望状态。失败时下一步：先确认集合已经加载；http 或 file 解析失败时，文档允许用 payload 作为备用代理，这只说明内容来源，不代表测速通过。然后再分别验证筛选表达式和健康检查字段。不要用更新集合的 interval 去替代 health-check.interval。两者单位都可以是秒，语义分别是集合更新周期和延迟测试周期。把两套字段看成一步，就会把“没测”和“筛错”搅在一起。
