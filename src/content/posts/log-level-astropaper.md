Clash 的 debug 日志之所以可能带出更多隐私线索，不是因为它单独定义了一种“隐私字段”，而是因为官方把这一档规定为：尽可能输出运行中所有的信息。级别越高，被写进控制台和控制页面的运行细节越多；这些细节一旦包含地址、域名解析过程、连接与策略相关的运行痕迹，被旁人看到或被复制走的风险就高于只保留错误摘要的级别。理解这一点，才能决定何时短时打开 debug、何时必须降回去。

## 适用条件：何时需要讨论 debug 与隐私

本说明适用于：你准备把 `log-level` 设为 debug 以排查问题；你已经在 debug 下拿到完整输出，需要判断能否转发、截屏或长期保存；或多人共用同一台设备的控制台、控制页面。若当前是 silent，官方定义为不输出，讨论“日志里的隐私”没有对象。若当前是 error 或 warning，输出被限制在错误类范围，线索少于 debug，但仍可能包含与故障直接相关的信息，不能认为低级别就“没有敏感内容”，只是覆盖面更窄。

官方还写明：内核日志仅在控制台和控制页面输出。因此隐私暴露的路径，首先是这两处的实时输出以及你从这两处复制出的文本，而不是文档未记载的其它渠道。讨论适用边界时，以“谁能看见控制台/控制页面、输出会不会被转存”为准。

## 用官方级别定义解释“为什么更多”

五个取值是递进关系，不是互相无关的开关。silent 不输出。error 仅输出发生错误至无法使用的日志，范围最窄。warning 增加“发生错误但不影响运行”的日志，并包含 error。info 再增加一般运行的内容，并包含 error 与 warning。debug 在此之上“尽可能”输出运行中所有的信息。所谓“更多隐私线索”，直接来自最后一档的“所有”和“尽可能”：凡是运行过程中内核愿意写出的信息，debug 都倾向于放出来，而不再按“是否已经无法使用”或“是否只是一般运行摘要”做强过滤。

因此，debug 比 info 更容易出现与完整运行路径相关的线索：一般运行内容在 info 已存在，debug 则进一步把尚未被前几级收录的运行信息也包括进来。这些信息本身是为排查准备的，但完整路径往往比一句“错误至无法使用”更能关联到具体访问目标、本地环境与策略决策。文档示例配置是 `log-level : info`，说明常规情况下并不需要以“所有运行信息”作为默认对外可见的输出。

判断是否“已经过多”的依据：若你只是要确认是否存在致命错误，error 已覆盖“无法使用”；若只要非致命错误，warning 已足够；若只要一般运行过程，info 已包含一般运行内容及更低级别。只有当前几级无法解释现象时，debug 的额外信息才有排查价值；多出来的那一部分，也正是隐私面上需要额外控制的部分。

## 操作上如何限制暴露以及失败时下一步

具体做法是：仅在需要完整运行信息的时间窗内，把全局配置中的 `log-level` 写成 debug；复现问题并只从控制台或控制页面读取与本次故障相关的片段；一旦已经定位或已经确认 debug 仍不足以解释，立刻改回 info（与文档示例一致）或更低。不要把 debug 输出发到公开渠道；若控制页面或控制台所在环境有其他人可访问，排查期间应意识到官方并未给这两处输出再套一层单独的隐私过滤。

若必须用 debug 但担心线索过多：先用 info 确认“一般运行内容”里已经有哪些，再开 debug 对比多出来的部分，只保留多出来且与故障直接相关的行，避免整段复制。若改成 debug 后并没有明显多于 info，下一步检查取值是否拼写正确、当前内核是否加载了该配置、你是否正在看官方指定的控制台或控制页面。若 debug 输出多到无法筛选，回到按级别降级：能用 warning 或 error 说清的，不要停留在“尽可能所有信息”。排查结束仍停留在 debug，等于让完整运行信息持续出现在可被查看的两处输出上，这与文档把 info 作为示例写法的取向不一致。
