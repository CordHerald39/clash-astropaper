准确与否取决于第一条命中的规则是不是对该请求的本意，不取决于列表有多长。规则按从上到下顺序匹配，顶部优先。条目增加后，只要有一条更靠上的宽规则先成立，后面写得再细也不会被看到。因此规则变多常常降低而不是提高准确性。

## 适用条件：怎样判断不准

不准确指：请求命中了非预期出站，或本该由后面某条处理的流量被前面截走。适用于列表中同时存在宽匹配与窄匹配的配置。若只有一条 `MATCH`，不存在多条互相抢先的问题。

判断依据：对同一目标，从上到下第一条满足条件的规则决定结果。`DOMAIN` 只匹配完整域名；`DOMAIN-SUFFIX` 按后缀；`DOMAIN-KEYWORD` 按关键字；`DOMAIN-WILDCARD` 使用 `*` 与 `?`；`DOMAIN-REGEX` 使用正则；`GEOSITE` 匹配集合内域名。后几种都可能一条覆盖大量主机。列表越长，越难保证这些宽规则都排在不会误伤的位置。

另一依据：udp 且节点无 udp 支持时继续向下匹配。条数多时跳过路径变长，看起来像不准，实际是出站能力与列表顺序的交互。

## 条数增加如何损害准确性

宽规则若插在窄规则之上，例如先写关键字或正则，再写某站的 `DOMAIN`，完整域名永远轮不到。内核没有最具体优先，只有顺序。`DOMAIN-WILDCARD` 与后缀的覆盖范围不同，叠在一起必须人工保证先后。

集合类规则隐含大量条目。`GEOSITE` 与 `RULE-SET` 在列表里各占一行，内部却是一批条件。把单条 `DOMAIN` 追加在集合之下，无法纠正集合已经做出的决定。表面上条数增加了，可纠正的空间反而变小。

目标 IP 规则可能触发 dns。匹配 `IP-CIDR`、`GEOIP`、`IP-ASN` 等一旦解析成功，后面按域名分流的规则不会执行。IP 类越靠上，域名意图越容易被覆盖。`no-resolve` 可跳过解析，但若更早规则已经解析过，带 `no-resolve` 的目标 IP 规则仍可能命中。多写几条 IP 规则并不会让域名判断更准。

逻辑规则中，`OR` 使任一 payload 成立即命中；`NOT` 使不满足某条的流量命中。为覆盖更多情况而叠加 `OR`，准确性通常下降。`AND` 虽能收窄，括号错误时行为与阅读理解不一致。`SUB-RULE` 把流量导入另一张表，总条数增加的同时更难看清最终生效的是哪一条。

进程、端口、入站条件与域名规则混排时，`PROCESS-NAME` 或 `DST-PORT` 可能先于域名命中，站点级预期全部失效。这不是这些类型本身无效，而是多出来的抢先机会变多了。

## 越加越不准时下一步

先停止追加。从列表顶向下标出第一条能匹配问题请求的规则，核对其类型是否宽于本意。若是关键字、正则、通配符或集合，把真正要优先的完整 `DOMAIN` 或明确后缀放到该宽规则之上，或收窄、下移那条宽规则。

若不准来自 IP 类：先决定该请求应以域名为准还是以 IP 为准。以域名为准则给 IP 规则加 `no-resolve` 或下移到域名规则之后；以 IP 为准才保留解析。不要靠堆叠更多 `GEOIP` 来补救顺序问题。

逻辑规则导致的不准：拆成单条并确认括号，能用单条类型解决的不要用 `OR`。通配符与正则须与配置其他处的 Clash 格式通配符区分。最后保留 `MATCH` 作为无条件终点。更少、更窄、顺序正确的规则，比更长的列表更接近每条都符合本意。
