## 优先级约束在什么条件下改变结果

Clash 对应的 MetaCubeX/mihomo 路由规则把策略选择建成一次线性扫描。官方优先级只有一条硬约束：规则将按照从上到下的顺序匹配，列表顶部的规则优先级高于其底下的规则。最终策略不是多条规则投票，也不是按类型“更具体就一定赢”，而是第一条条件成立的规则说了算。顺序之所以能改变结果，前提是同一请求上至少有两条规则同时可能为真。

适用条件包括：域名类宽窄并存（完整域名、后缀、关键字、Geosite）、域名类与目标 IP 类并存、逻辑规则与普通规则并存，以及列表中出现 `MATCH`。判断依据很直接：只交换两条规则的上下位置、payload 不变，同一请求的出站策略随之切换。如果对调后结果完全不变，说明当前请求上并没有这两条同时为真，或还有第三条更靠上的规则已经截断。`MATCH` 匹配所有请求、无需条件，它的行位等于默认策略写在哪里；放在中部等于从该行起放弃后面所有细分规则，放在末尾才表示前面全部未命中时的兜底。

## 重叠如何从类型定义里产生

手册里的类型覆盖范围不同，因而天然重叠。`DOMAIN` 只对准完整域名。`DOMAIN-SUFFIX` 对准后缀，官方例子是 `google.com` 可匹配 `www.google.com`、`mail.google.com` 和 `google.com`，但不匹配 `content-google.com`。`DOMAIN-KEYWORD` 只要求关键字出现。`DOMAIN-WILDCARD` 使用 `*` 与 `?`，且与配置其他处的 Clash 格式通配符不相同。`DOMAIN-REGEX` 用正则。`GEOSITE` 按集合匹配域名。对同一个主机名，上述类型经常同时为真，这时文件中的先后就是唯一仲裁。

目标 IP 类会再引入“是否已经解析”。`IP-CIDR` 和 `IP-CIDR6` 效果一样，后者只是别名；还有 `IP-SUFFIX`、`IP-ASN`、`GEOIP`。域名开始匹配关于目标 IP 的规则时，mihomo 将触发 dns 解析；`no-resolve` 可跳过解析。但如在更早的匹配中触发了 dns 解析，则依旧会匹配到添加了 `no-resolve` 选项的目标 IP 类规则。于是“先写域名还是先写 GEOIP/CIDR”不仅改变谁先为真，也改变后面带 `no-resolve` 的规则还有没有机会按“未解析”来理解。

逻辑规则把多条 payload 组合：`AND` 要求同时成立，`OR` 任一成立，`NOT` 取反，并且需要注意括号。括号使一条逻辑规则的真值范围突然变宽或变窄时，只要它还和别的规则重叠，顺序微调就会表现为最终策略大变。`RULE-SET` 把集合插在当前行的优先级上，`SUB-RULE` 把匹配转入子规则，它们改变的是“这一整块”相对其他规则的位置。进程、端口、入站、`NETWORK` 再与域名条件交叉，同一连接上仍只取最上一条真规则。

另外，若请求为 udp，而代理节点没有 udp 支持（例如 ss 节点没写 udp: true），则会继续向下匹配。这时“条件命中某出站”并不等于扫描结束，顺序会继续作用于下一个候选。这是顺序影响最终策略的第二条路径：不是条件没成立，而是成立后的出站能力不足，匹配尚未结束。

## 调整顺序的操作与失败下一步

具体操作：列出该请求上所有可能为真的规则，严格按文件行序排列，确认第一真值对应的策略是否就是当前结果。若希望细规则生效，把更具体的类型移到更宽类型之上，例如完整 `DOMAIN` 高于 `DOMAIN-SUFFIX`，后缀高于关键字与 Geosite，需要按域名决策的条目高于过宽的 `GEOIP` 或提前出现的 `MATCH`。逻辑规则保持手册括号结构，例如 `OR,((NETWORK,UDP),(DOMAIN,baidu.com)),REJECT`。不重叠的规则对调通常不改变结果，判断依据仍是同一请求上是否存在多条同时为真。

失败时下一步：对调后策略不变，先把未计入的第三条找出来，常见来源是更上方的 `RULE-SET`、已被提前触发解析的目标 IP 规则，或过早的 `MATCH`。把列表缩到这几条再对调，避免在长列表里猜测。若只在 UDP 上出现“顺序失灵”，先核对节点是否具备 UDP 能力，而不是继续改域名规则先后。确认先后关系后，保持宽规则在下、细规则在上，并把 `MATCH` 留在最后作为无条件兜底。
