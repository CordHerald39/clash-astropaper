电脑上容易把系统代理当成总闸，以为打开后本机所有软件都会经过 Clash。官方全局配置并没有把操作系统里的代理登记写成覆盖全部应用、全部协议的开关。它说明的是：内核提供 http(s)/socks/mixed 一类代理端口；谁可以连接这些端口；连接进来之后按哪种运行模式处理；以及是否对进程做匹配。分清这几层，就能解释系统代理为什么不是统一开关，以及哪些检查有意义。

## 系统代理实际接管的流量

系统代理是操作系统提供给应用查询的 HTTP/HTTPS 代理设置。应用如果遵守该设置，就会把网页类请求发到 Clash 的 http 或 mixed 端口。入站上可以配置 authentication；skip-auth-prefixes 用来让特定源地址免密，文档示例包括本机回环 127.0.0.1/8 与 ::1/128。这些项只回答谁有资格连接代理端口，并不会把从未询问系统代理的程序强行接入。

allow-lan、bind-address、lan-allowed-ips、lan-disallowed-ips 进一步表明入站是端口服务，而不是网卡级总开关。允许局域网打开后，其他设备可以经 Clash 的代理端口访问互联网；绑定地址限制从哪个地址接受这类访问，* 表示绑定所有 IP，也可以只绑定单个 IPv4 或 IPv6；禁止列表优先于允许列表。它们管的是入站可达范围，不是全部进程的全部套接字。

因此，系统代理开启的含义很窄：遵守该设置的应用，多了一个指向 Clash 入站的出口。不查询系统代理的客户端、自行实现传输的程序，都不会因为这个开关改变路径。把“总闸已打开”当成覆盖一切的前提，后续排查会一直对错层。

## 运行模式和进程匹配各管什么

流量即使已经进入入站，也不等于走了代理节点。mode 默认 rule；global 需要在 GLOBAL 策略组选择代理或策略；direct 为全局直连。系统代理打开的同时把 mode 设为 direct，结果仍是直连，这常被说成开关无效。开关只决定流量是否送到 Clash，mode 才决定 Clash 如何处置这些流量。两者同时成立，才谈得上“走代理节点”。

find-process-mode 也常被理解成按应用强制代理。文档写明：always 强制匹配所有进程；strict 为默认，由 Clash 判断是否开启；off 不匹配进程，推荐在路由器上使用。进程匹配服务于规则里对进程的识别，前提是流量已经到达内核。它不能代替系统代理，也不能在只有 HTTP 入站时劫持那些从不使用系统代理的应用。路由器场景建议关闭进程匹配，更说明该选项与桌面系统代理不是同一个开关。

要观察真实路径，只能用日志和外部控制。log-level 在控制台和控制页面输出，验证时需要 info 或 debug，silent 看不到依据。external-controller 提供 API，文档示例为 127.0.0.1:9090，可设置 secret。没有入站连接记录时，讨论规则和进程匹配没有意义。

## 适用边界与失败后的下一步

适用条件是：需要解释或处理系统代理已开但某应用仍直连，或需要说明不能靠一个开关覆盖全部软件。判断依据是：遵守系统代理的应用，会在 http 或 mixed 入站留下日志或 API 连接；不遵守的应用在仅开启系统代理时不应出现记录；mode 为 direct 时，即使有记录也不应期望走代理节点。ipv6 默认允许内核接受 IPv6 流量，它同样不是总闸，只影响内核是否接受这类流量。

出现理解偏差或排查失败时，先用日志确认该应用有没有碰到入站。没有记录，说明系统代理不是它的统一入口，应检查该应用是否支持手动填写 HTTP 或 SOCKS，而不是继续切换 mode。有记录再看 mode 与 GLOBAL 组选择。认证失败则调整 authentication 或 skip-auth-prefixes。其他设备访问再考虑 allow-lan 与绑定地址。不要把 find-process-mode 设为 always，当作所有应用强制走系统代理的替代开关。需要更细记录时再开 debug，并确认 API 的 secret；经 socket 或 namedpipe 访问时文档写明不验证 secret，须自行控制访问范围。
